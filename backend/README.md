# CurioCircle community backend (staged)
This is not a public feedback release. The playable PWA remains at 0.9.4.1 (Beta). Do not merge or load community-client.js in the live app or enable public writes until the owner accepts the privacy review and end-to-end tests.

## Setup and deployment
- Run **CurioCircle backend setup (feedback disabled)** in GitHub Actions on main. It uses the existing CLOUDFLARE_API_TOKEN secret, verifies the expected account/database via hashes and EU jurisdiction, validates catalogue and local Worker smoke tests, applies the additive schema, syncs only IDs/categories (not user information), deploys curiocircle-api with FEEDBACK_ENABLED=false, disables Worker observability and logpush, disables previews, and checks the deployed health and access controls. No feedback rows are inserted during deployment. If the workers.dev subdomain is not configured, configure it in Cloudflare and rerun; don't publish data until the workflow is green.
- Never print API tokens, admin keys, vote receipts or user submissions in CI logs or public artifacts. No deployment credentials in browser code. GitHub workflow only on main pushes to backend implementation paths or manual dispatch; no PR-triggered deployment.
- In Cloudflare Worker settings, create a secret named ADMIN_TOKEN using a password manager to generate a high-entropy value (at least 32 characters). Never share it in chat. Existing secret bindings are retained on backend redeploy. Open the Worker URL followed by /admin and enter the secret; it is held only in memory. No public admin read/write access without this key.
- The dashboard currently supports aggregate counts by question/category/language, moderation status, and CSV. Suggestions are not published automatically. Review exact and semantic duplicates against questions.json, suitability, categories and six-language translations manually before catalogue publication. CSV export sanitizes spreadsheet formulas. Initial list is limited to 500 suggestions; pagination and aggregate review views are still required before scaling.
- Each deployment keeps public feedback disabled. Future activation must be a deliberate reviewed release, not an automatic consequence of setup. Keep the public PWA functional without the backend.

## Data design
- D1 contains catalogue ID/category, optional votes with question-specific random receipt hash, revision, vote, language, app version and day; a withdrawal is a NULL vote tombstone so older retries do not recreate the vote. No universal device/user ID. Receipt is stored locally; loss of local storage means the old vote cannot be modified from that device. It is impossible to verify unique humans with this design; do not claim that each vote equals a distinct person. Local receipts are currently separate from the existing backup/reset; integrate backup/reset and clear queue semantics before launch.
- Suggestions contain only explicit text, language, a random submission receipt hash, duplicate hash, status and dates. They are quarantined for human review. The API rejects obvious URLs, email addresses and long digit strings, but cannot guarantee that no personal data appears in free text. Warn users before submission. Exact duplicate submissions are suppressed; catalogue/semantic duplicate checking and content moderation remain human work.
- Request size and field allowlist, parameterised SQL, strict origin check and global hourly write caps. Origin is not authentication, global caps do not prevent distributed spam. Before activation, review abuse protection (e.g. provider-native rate limiting without storing IPs in D1). No application IP logging, tracking cookies or analytics. Cloudflare can still process IPs/technical data in infrastructure and security systems, and D1 EU storage does not imply all Worker processing occurs in the EU.
- Decide/document controller contact, processor agreements and international transfers, lawful basis, retention and deletion policy before activating. Proposed default: periodic purge of rejected submissions after 90 days, vote data/tombstones after a defined retention period (e.g. 12 months), hourly counter rows older than 48 hours; implement the cleanup and test its effect on idempotency before launch. Never advertise absolute anonymity.
- Frontend module staged with six languages, voluntary buttons, editable/retractable ratings, durable queue, offline retries, explicit suggestion submission, pending/confirmation messages. It is not mounted into production or end-to-end verified. Before release: add visual components, localised privacy text including provider and retention, feature gate, queue cancellation/reset/import, offline first-load behaviour, accessibility/device checks, test real writes with synthetic data then remove only synthetic rows, confirm admin auth and CSV, and get approval.
